# GitHub REST collection limits and safe concurrency

## Summary

A local Actions collector should request `per_page=100`, follow the response `Link` header, and split workflow-run queries into bounded `created` windows whenever a filtered search could exceed GitHub's documented 1,000-result ceiling. Authenticated user requests normally share a 5,000-request/hour `core` budget **per user, not per token**; GitHub's only documented safe concurrency guidance is serial execution, despite a secondary-limit ceiling of 100 concurrent REST-plus-GraphQL requests.

For a bounded multi-token collector, keep one aggregate queue, treat tokens belonging to the same user as one primary-rate bucket, preserve validators per exact URL, and react to response headers and `403`/`429` responses. Multiple tokens do not make concurrency below 100 guaranteed safe because secondary limits can change without notice and include undisclosed triggers.

## Findings

1. **Actions list pagination and caps** — Both repository/workflow run listings and workflow-job listings default to 30 and accept at most 100 results per page. Follow `Link` URLs rather than constructing pages. GitHub documents a maximum of 1,000 results **for each workflow-run search when any of** `actor`, `branch`, `check_suite_id`, `created`, `event`, `head_sha`, or `status` is used. Therefore, use bounded `created` ranges and subdivide any range whose `total_count` reaches or exceeds 1,000; the documentation does not state a 1,000-result cap for an unfiltered run listing or for job listings. [Workflow runs](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28) [Workflow jobs](https://docs.github.com/en/rest/actions/workflow-jobs?apiVersion=2022-11-28) [Pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api?apiVersion=2022-11-28)

2. **Workflow attempts matter** — `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs` defaults to `filter=latest`; `filter=all` includes old executions, while `GET /repos/{owner}/{repo}/actions/runs/{run_id}/attempts/{attempt_number}/jobs` targets one attempt. Each jobs endpoint has `per_page` max 100. A collector that needs rerun history must explicitly use `filter=all` or enumerate attempts; the default silently represents only the latest execution. [Workflow jobs](https://docs.github.com/en/rest/actions/workflow-jobs?apiVersion=2022-11-28)

3. **Primary/core budgets are identities, not token counts** — Unauthenticated requests receive 60 requests/hour per originating IP. Requests authenticated on behalf of a user—including personal access tokens and GitHub/OAuth app user tokens—normally share that user's 5,000 requests/hour budget; issuing multiple PATs for one user does not multiply capacity. GitHub Enterprise Cloud app-on-behalf-of-user cases can have 15,000/hour. Installation access tokens have their installation's separate budget: normally at least 5,000/hour, 15,000/hour for Enterprise Cloud organizations, and eligible non-Enterprise installations can scale to 12,500/hour. [Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28)

4. **Secondary limits are aggregate operational constraints, not extra token quotas** — GitHub documents no more than 100 concurrent requests shared across REST and GraphQL, no more than 900 REST endpoint points/minute (most `GET`/`HEAD`/`OPTIONS` calls cost one point), and no more than 90 seconds of API CPU time per 60 seconds of real time. These limits can change without notice, some endpoint point costs are undisclosed, other undisclosed triggers exist, and there is no endpoint/header that reports remaining secondary capacity. Token rotation therefore cannot be treated as a safe bypass. [Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28)

5. **The documented concurrency recommendation is serial** — GitHub explicitly recommends making requests serially with a queue to avoid secondary limits. Thus the conservative collector default is one aggregate in-flight request across tokens. If bounded parallelism is retained as a throughput compromise, it should be a low configurable aggregate bound, never approach 100, and reduce to serial/back off on secondary-limit responses; GitHub provides no documented concurrency value greater than one that it calls safe. [Best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api?apiVersion=2022-11-28)

6. **Conditional requests save primary budget only under precise conditions** — Save `ETag` (most endpoints) or `Last-Modified` (many endpoints) for the exact stable URL and send `If-None-Match` or `If-Modified-Since`. An unchanged, correctly authorized conditional `GET` returns `304 Not Modified` and does not count against the primary rate limit. Keep page size, page number, filters, media type, and API version stable because a different representation has a different validator. GitHub does **not** say that a `304` is exempt from secondary limits, so conditional polling still belongs in the same queue. [Best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api?apiVersion=2022-11-28)

7. **Headers sufficient for bounded scheduling** — Consume `Link` (`rel="next"`) for pagination; `ETag`/`Last-Modified` for validators; `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-used`, `x-ratelimit-reset` (UTC epoch seconds), and `x-ratelimit-resource` (expect `core` for these REST calls) for primary-budget state; `Retry-After` for enforced delay; and `x-poll-interval`, if present, as the minimum repoll interval. `x-github-request-id` is useful for diagnostics but not scheduling. Prefer these response headers to polling `GET /rate_limit`: that endpoint does not consume primary quota but can consume secondary quota. [Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28) [Best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api?apiVersion=2022-11-28) [Pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api?apiVersion=2022-11-28)

8. **Required stop/backoff behavior** — Primary exhaustion returns `403` or `429` with `x-ratelimit-remaining: 0`; wait until `x-ratelimit-reset`. A secondary limit returns `403` or `429` with an explanatory message: honor `Retry-After` first; otherwise, if remaining is zero, wait for reset; otherwise wait at least one minute, then use exponential backoff and a finite retry cap. Continuing while limited risks integration banning. [Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28)

## Collector decision gist

Use 100-item pages plus `Link`, recursively split filtered `created` windows before the 1,000-run ceiling, fetch jobs only for selected runs (and explicitly choose latest versus all attempts), serialize an aggregate multi-token queue by default, key primary budgets by authenticated identity/installation rather than token string, cache validators per exact request URL, and gate retries on `Retry-After`/rate-limit headers.

## Gaps

- GitHub does not document the scope at which the 100-concurrent-request secondary ceiling is aggregated, nor all secondary-limit triggers or endpoint point costs. The brief therefore does not claim that any parallel value is guaranteed safe.
- GitHub does not document a 1,000-result cap for unfiltered Actions run lists or job lists. This is an absence of a documented cap, not proof that no service-side bound exists.
- The docs say “for each search” when listed run filters are used, but do not define boundary behavior for equal timestamps. A future implementation should use overlap plus run-ID deduplication when splitting `created` ranges.
- No live authenticated API calls were made, so endpoint-specific presence of `ETag`, `Last-Modified`, or `x-poll-interval` was not empirically confirmed; the docs intentionally say “most,” “many,” and “if present.”
