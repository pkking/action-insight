# ADR-024: Evidence-aware PR card-hours and coverage audit

### Daily trend calendar ownership (2026-10-31)

Daily trend candidates are bounded by run creation, attempt start, job creation, or job execution overlapping the reporting window; once a run qualifies, its native rows remain available for evidence and coverage. An undated NPU attempt is counted only when its own run, attempt or jobs are window-relevant, not merely because a different attempt on the same run qualifies. Per-repository evidence and exclusion counters overlap and do not establish missing collection or unknown hardware identity. This bounded query preserves pre-window runs that cross into the window while excluding unrelated historical runs; it does not change collection or stored data.

Daily trends use three distinct UTC anchors: split each eligible job's execution interval at UTC midnights for physical card-hours; attribute valid job created-to-started queue samples to job creation day; attribute NPU-evidence native attempts to their own `run_started_at` day. Unlike the earlier run-created monthly audit, qualifying jobs and attempts on runs created before the window must remain eligible. Missing timestamps are never borrowed from the run. The separate workflow-by-day collection audit retains run-created attribution and cannot prove collection completeness. Preserve nulls and show community coverage separately from metric evidence; seven-day means require seven consecutive non-null daily values and exclude incomplete current days. These are observed occupancy and wait samples, not utilization or evidence of causation.

**Status**: Accepted (conservative reporting rules); implementation is incremental

## Context

The PR efficiency report (including `reports/npu-pr-efficiency-2026-10.py`) combines PR artifact links, workflow attempts, jobs, runner evidence, and resource counts. The existing reports distinguish some unknown resources, but their aggregate tables can still be misread as complete community totals. Cross-month comparisons are especially sensitive to partial windows, missing artifacts, reruns, mixed-resource workflows, stale local snapshots, and runner labels that identify a platform but not the number of physical accelerators.

The requested analysis covers 2026-08 through 2026-10. Inspection of the checked-in October report found it was generated at **2026-10-30 10:20:48 UTC**, with read-only repeatable-read access, and deliberately compares runs created on days 1–30 only (October remains snapshot-limited). A separate read-only local PostgreSQL snapshot at **2026-10-30 10:49:45 UTC** confirmed available run data across the requested dates: August 6,108 runs / 5,221 `pull_request` event runs; September 43,765 / 30,374; October 91,627 / 63,378. These are database-wide counts, not allowlist or NPU counts. The snapshot was explicitly `transaction_read_only=on`, `repeatable read`; hourly collectors were concurrently active, so these counts describe a point-in-time observation, not a frozen historical dataset.

The existing October report's allowlisted, day-1-through-30 PR-event candidate data reports 3,347 / 21,321 / 38,129 runs for Aug/Sep/Oct, and 3,347 / 21,400 / 38,361 event attempts (the latter uses stored attempts, with a missing-row fallback). Its linked NPU attempts are 0 / 1,229 / 7,709, while NPU-evidence attempts lacking PR links are 903 / 9,320 / 16,070. This demonstrates that a missing PR link is not evidence of zero CI; these numbers are a dated report snapshot and should not be silently presented as current or complete.

Existing contracts constrain this work: ADR-017 makes `etl/repos.yaml` the reporting inventory and prioritizes explicit `static_resources`; ADR-018 keeps resource dimensions separate and forbids guessing unknown quantities; ADR-020 defines attempt-level attribution and PR card-hours; ADR-023 makes rerun durations attempt-scoped. The local `ci-effective-report` skill is read-only and forbids GitHub API calls. No historical backfill may use a narrow time window as if it were a complete PR-metrics rebuild.

## Decision

1. **Separate evidence states.** Every reported resource amount must be one of:
   - **Known**: the job/attempt is identified, its elapsed runtime is valid, and resource type and positive physical-card quantity are explicitly supported by job metadata or an applicable, versioned configuration rule.
   - **Estimated**: an explicitly declared estimation rule is applied to identified evidence, with its rule, inputs, assumptions, and covered sample count disclosed separately from known totals. Estimates must never be folded into known totals.
   - **Unknown**: any required identity, timing, resource type, quantity, or mapping evidence is missing, stale, contradictory, or invalid. Unknown is not zero and is excluded from numeric known totals while remaining countable.

   Generic runner/platform names (including a generic NPU/Ascend name) do not establish card count. No inferred one-card default is permitted. A future estimate policy that materially changes user-facing totals requires a separately reviewed configuration/ADR decision; until then the report uses no estimated card-hours.

2. **Use attempt- and job-scoped evidence.** For this coverage audit, the sample is all `pull_request`-event runs matching `config/drilldown-workflows.yaml`, regardless of PR links. Only native `workflow_attempts` and `workflow_jobs` are used; no synthetic attempt or legacy job fallback. A PR event is not proof of a confirmed PR identity. Deduplicate at `(repo, run_id, run_attempt, job_id)` and never multiply jobs by PR links. PR attribution in other reports remains governed by ADR-020.

3. **Respect period boundaries and freshness.** This audit uses UTC `runs.created_at` in `[2026-08-01, min(2026-11-01, snapshot))`, not a day-1-through-30 slice. October is snapshot-limited. Record exact bounds and snapshot in the artifacts; do not combine overlapping snapshots or silently fill absent days.

4. **Handle heterogeneous workflows at job level.** A workflow may contain NPU, CPU, and unclassified jobs. Classify each job independently from job labels, resource metadata, and governed mappings; workflow names alone are not hardware evidence. Report NPU evidence, other identified resources, and unknown jobs distinctly. `static_resources` may describe an explicitly configured workflow requirement but must not be applied as a job-level physical allocation to a mixed matrix unless the configuration explicitly scopes that requirement to those jobs.

5. **Preserve dimensional correctness.** The versioned `governed-runner-v3` audit accepts the existing runner convention in `etl/scripts/collect.ts` (`parseRunnerResourceLabels`) and `.agents/skills/ci-effective-report/scripts/ci_analyze.py` (`_resource_type_and_cards`) as unit evidence, restricted to the explicit model inventory in the audit. A2 variants, 310P and A5 suffixes represent physical cards; A3, A3-800i, A3-800t and nightly-A3 use `(N+1)//2` once. Explicit `-N-cards` means N physical cards; explicit A3 dies use the same conversion. Stored model/count matching this convention are raw suffix values, not already-normalized cards. Contradictory metadata/labels or unsupported quantities remain unknown. CPU `cpu-N` is not NPU cards; GPU and mixed hardware are separate. Generic names and arbitrary substrings cannot establish counts, and no default of one is allowed. Governed conventions are not proof of historical runner configuration or effective dates. Only completed non-skipped jobs with nonnegative elapsed time and known positive physical quantity contribute; zero duration is valid, negative duration is not clamped. Failure and cancelled jobs retain valid occupancy. Time, execution, hardware and quantity states are separate and can overlap. Card-hours represent attributed job occupancy, not capacity, utilization, cost, waste, or unique wall time. Do not combine unlike models.

6. **Audit coverage before interpreting totals.** Show all allowlisted repo/workflow/month combinations, PR-event runs, native attempts, missing-attempt runs, zero-job attempts by status and `jobs_fetched_at` presence, and job resource/time evidence. Null `jobs_fetched_at` does not prove an unfetched attempt; without an expected count neither a zero-job attempt nor a partial set confirms missing collection. A zero measured subtotal is distinct from no eligible observations; missing rows are not zero work. No estimated quantities are used. The audit does not infer a historical effective date for the current allowlist or labels.

## Alternatives and trade-offs

- **Assume one card for an NPU runner**: simple and produces broad totals, but fabricates quantities and systematically misstates mixed hardware; rejected.
- **Infer card counts from workflow names or historical neighboring jobs**: increases apparent coverage but can cross runner generations, matrix variants, or configuration changes; rejected as a default. A separately labelled estimate may be considered only with explicit, time-bounded mapping evidence.
- **Use only PR-linked runs**: produces cleaner attribution but hides substantial unlinked PR-event work in the observed dataset; rejected as the sole coverage view. Linked metrics remain separate from unlinked candidates.
- **Backfill GitHub artifacts immediately**: could improve linkage but consumes API quota, mutates shared database state, and concurrent collectors are running; deferred. Do not run collection/rebuild while unrelated ETL is active without an explicit safe coordination window and scope.
- **Call day-1-through-30 a full month**: simplifies labels but excludes day 31 and understates month totals; rejected. Keep the common cutoff explicit and treat a full-month view separately.

## Scope and consequences

This decision governs the reproducible NPU/PR coverage audit and future PR card-hours/report presentation. It does not change schemas, ETL collection behavior, PR-link resolution, resource-pool calculations, or invoke GitHub APIs. It does not authorize any production database writes or historical rebuilds.

Expected consequences: lower but defensible known card-hour coverage; explicit unknown/estimated counts; visibility of unlinked candidates; potentially more detailed per-job diagnostics for mixed workflows; and additional provenance/configuration maintenance. Historical report values are point-in-time snapshots and must not be retroactively described as complete totals without rerunning a safe, read-only audit.
