# ADR-007: Migration from Turso (libSQL) to self-hosted PostgreSQL

**Status**: Implemented (Turso removed; `pg` native, `PG_DATABASE_URL`, Docker Compose, SQLite fallback deleted)
**Date**: 2026-08-07
**Context**: Turso (libSQL) free/starter-tier write limits repeatedly blocked scheduled CI collection

## Context

The Action Insight ETL pipeline was using Turso (managed libSQL/SQLite cloud)
as its primary database backend. Turso's free/starter tier imposes write
limits that were repeatedly hit during scheduled CI data collection, causing
`isTursoWriteBlocked` errors and stalling data ingestion. The codebase had
grown a SQLite fallback layer (`sqlite-storage.ts`, `isSqliteFallbackEnabled`,
`writeWithOptionalSqliteFallback`) as a workaround, adding dual-write
complexity across the ETL pipeline.

## Decision

Migrate the entire storage layer from `@libsql/client` (Turso) to `pg`
(node-postgres) backed by a self-hosted PostgreSQL instance deployed via
Docker Compose. This eliminates artificial write limits and simplifies
operations.

Key decisions:

1. **Full pg native rewrite**, not an adapter layer. All `?` placeholders
   become `$N`, all `execute()` become `query()`, all `transaction()`/`batch()`
   become pg-native `BEGIN`/`COMMIT`/loop. This produces idiomatic, maintainable
   pg code with no abstraction layer to debug.

2. **Drop SQLite fallback entirely.** `sqlite-storage.ts`,
   `isSqliteFallbackEnabled()`, `writeWithOptionalSqliteFallback()`, and all
   dual-write code paths are removed. Self-hosted PG is reliable enough;
   dual-write was a workaround for Turso's cloud limitations.

3. **Docker Compose deploys the entire stack** (app + db), not just PostgreSQL.
   The `app` service builds the Next.js image and connects to the `postgres`
   service via `PG_DATABASE_URL`.

4. **Environment variable renamed to `PG_DATABASE_URL`** (no `TURSO_AUTH_TOKEN`).

5. **Schema conversion**: GitHub ID columns use `BIGINT` (64-bit) instead of
   SQLite's `INTEGER`. Auto-increment columns use
   `GENERATED BY DEFAULT AS IDENTITY` instead of `AUTOINCREMENT`. Default
   timestamps use `NOW()::TEXT` instead of `strftime(...)`. Boolean-like
   columns remain `INTEGER` (0/1) to avoid changing the data-access layer.

6. **Placeholder conversion utility** (`toPgSql()`): converts SQLite-style `?`
   placeholders to PostgreSQL `$N` numbered placeholders. This allows existing
   SQL query strings to remain unchanged in most of the codebase, reducing
   migration risk.

## Trade-offs

- **Lost**: Turso's managed cloud convenience (no server to maintain, automatic
  backups, edge replication).
- **Gained**: Unlimited writes, local development parity, simpler ops, no
  dual-write complexity, no write-block error handling.
- **Risk**: Self-hosted PG requires operator-managed backups and updates.
  Mitigated by Docker volume persistence and the simplicity of a single-host
  deployment.

## Impact

- All storage code uses `pg`; `@libsql/client` removed from dependencies.
- `pg/schema.sql` is the canonical schema; `turso/schema.sql` is retained for
  historical reference.
- Docker Compose is the canonical deployment method.
- The Turso→PG migration script (if needed) will use `@libsql/client` as a
  temporary devDependency to read from the old Turso instance.
- CI workflows need to be updated to install `pg` instead of `@libsql/client`
  and pass `PG_DATABASE_URL` instead of `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN`.
